> `reports\完整汇报_甲方第一人称_2026-10-24.md:239-241`
> "**需要甲方定口径的部分**：`extra`（多余材料）是否纳入指标；若纳入，我方按第四节的
> 5 处改动排期，并需要甲方提供候选网格面号。"

我没有停在"这是口径问题"。实测之后我发现它同时是一个**可以自证的代码缺口**：

1. 检测器对每件真实件都会报 extra 区域。我对 `outputs\**\result.json` 全量扫了一遍
   （**197 份 result.json，706 个 extra 区域**），结果是
   **706/706 个 extra 区域的 `candidate_face_ids` 非空、`reference_face_ids` 全为空**
   （命令见第七节 E2E 脚本的扫描段；这是"多余材料的真值在候选网格上"的实测依据）。
2. `learning\annotation_scoring.py` 此前明确只打 missing：
   `_SCORABLE_DEFECT_TYPES = ("missing",)`，并在模块注释里写明
   "extra 的真值在候选网格上，schema 里没有对应字段，硬凑会算错"。
3. 标注 schema（`learning\annotations.py`）此前只有一个面号字段
   `reference_face_ids`；`scripts\bootstrap_annotations.py` 对 extra 区域照抄它，
   于是**候选面号在草稿这一步就被丢掉**。
4. 复核表（`learning\annotation_review.py`）的 `face_count` 也只数
   `reference_face_ids`——extra 行显示 **0 个面**，复核人看到"0 个面"会以为
   这块多余材料没有面号可判，直接把它剔掉，而它恰恰是 extra 唯一的真值来源。

所以这不是"要不要纳入指标"的问题，而是**链子差一环**：即使甲方把多余材料
全部标好，`score-annotations` 也算不出这一类结论的准确率，只能给一句
"extra 类缺陷未打分"。我这一轮就是把这一环接上。

## 二、我改了什么（逐项）

> 红绿口径与本项目一致：先写一条会失败的用例（红），再改实现让它通过（绿）。

### FIX-A 标注 schema 升到 1.1：承认"extra 的真值在候选网格上"

文件：`src\cad_inspector\learning\annotations.py`

- `SCHEMA_VERSION` 由 `missing-region-annotations-1.0` 升到 `...-1.1`；
  新增 `_LEGACY_SCHEMA_VERSIONS = ("missing-region-annotations-1.0",)` 与
  `_ACCEPTED_SCHEMA_VERSIONS`，**1.0 仍可读**。
- 新增 `candidate_face_ids`（长度不定的非负整数数组，区域内部不许重复）。
- 1.1 起对 `extra` 区域两条硬约束：
  ① 必须给非空 `candidate_face_ids`（缺了它这一类无法打分）；
  ② 不许同时给 `reference_face_ids`（多出来的料在参考件上并不存在，
  两侧都填说明标注人自己也没分清真值在哪张网格上）。
- 版本判定按**文件自己的版本**走，不归一成当前版本：1.0 里没有这个字段，
  按 1.1 的严格规则读会把存量草稿判成非法数据。

**为什么必须留 1.0 兼容（实测）**：`reports\draft_annotations.json` 是
`schema_version=missing-region-annotations-1.0`、**18 条记录 / 64 个 missing + 91 个 extra 区域**
的存量草稿，已被 `tests\test_bootstrap_annotations.py` 当审计材料在读；
`tests\test_cli_commands.py` 也有一份 1.0 的清单用例。升版顺手把它们烧掉，
等于毁掉既有证据。

### FIX-B 打分器按缺陷类型选真值字段

文件：`src\cad_inspector\learning\annotation_scoring.py`

- `_SCORABLE_DEFECT_TYPES = ("missing", "extra")`；
  新增 `_TRUTH_FACE_FIELD = {"missing": "reference_face_ids", "extra": "candidate_face_ids"}`，
  `_face_ids()` 按类型取字段（预测侧同样口径：result.json 里 extra 区域也是
  `candidate_face_ids`）。
- 结果里新增 `truth_face_field`，事后核对不用猜"这个 recall 是拿哪一侧面号算的"。
- 新增 `score_annotations_multi()`：一次跑多类，**分列**报告；整体状态只在
  每一类都是 `SCORED` 时为 `SCORED`，否则有确认记录就是 `PARTIAL`、都没有就是
  `NO_CONFIRMED_RECORDS`。
- **防"假 0 召回"守卫**：目标类型的真值字段整个缺失时**直接报错**，
  不返回数字。理由：1.0 清单没有 `candidate_face_ids`，按空真值算会把每个预测
  都记成假阳性、召回记成 0——那是一个看起来完全正常的数字，却是"没数据"造成的。
- `limitations` 里写清 extra 的编号依赖：候选面号是**三角化结果**的编号，
  必须与预测使用同一套三角化参数（草稿记录的 `source_linear_deflection_mm`）。

### FIX-C 复核表：extra 行数候选面号 + 整件判定静默忽略护栏

文件：`src\cad_inspector\learning\annotation_review.py`

- `SHEET_COLUMNS` 新增 `candidate_face_count` 列；`face_count` 改成**按缺陷类型**
  取真值面数（missing 数参考面、extra 数候选面）。
- 新增护栏：给**有区域**的件填写 `scope=record` 的整件判定行时直接报错。
  这类行会被按区域判定的循环覆盖，属于**静默丢掉人工填的一格**——填表的人
  以为自己的判断生效了，实际那条判定从未进过清单。

### FIX-D 草稿生成：extra 写候选面号，missing 清空候选面号

文件：`scripts\bootstrap_annotations.py`

- `_region_to_draft()` 按类型写面号：extra → `candidate_face_ids`（候选网格）；
  missing → `reference_face_ids`（参考网格）。
- missing 区域里那份 `candidate_face_ids` 是"采样落点"（每个参考面的采样点在
  候选件上的最近三角面），**不是真值**；我清空它，避免被 extra 口径当成真值

### FIX-E CLI：`score-annotations --defect-type missing|extra|both`

## 六、我保留的限制（不许被读成"extra 已经准了"）

1. **这条链只证明"算得出来"，不证明"算得准"。** 真实件上 extra 的准确率仍然
   零证据：`README.md` 里那条"extra 只在合成真值上验证过"没有变。
   要拿到数字，必须甲方按 `验收操作手册.md` 第 3 步人工复核 extra 行。
2. **extra 的面号口径依赖三角化参数。** 候选面号是候选件三角化网格的编号，
   与预测必须同参；换精度就换编号（草稿里的 `source_linear_deflection_mm`
   记着这一套参数）。这条已写进打分报告 `limitations`、手册与 README。
3. **面级口径不变**：不做法向/距离容差；区域级匹配（质心距离 / IoU）留待与
   甲方约定命中口径后再加。
4. **1.0 存量清单打不出 extra**：它没有 `candidate_face_ids`。这不是静默跳过，
   是明确报错；要打 extra 必须用当前版本 `bootstrap-annotations` 重新生成草稿。
5. **训练集/1（453.7MB / 178 万面）仍要换大内存机器**：这是外部机器约束，
   我这一轮没有动它，也没有为了让报告好看而降低采样口径。
