────────────────────────────────────────────
零、一句话结论
────────────────────────────────────────────
这条用例**不是**代码回归，也**不是**嵌套 pytest 在负载下"漂移"。
它的断言要求一个**只有在子进程干净跑完时才会出现**的正面证据
（失败用例名）。只要内层 pytest 因为**环境**原因异常收场
（超时被杀、或临时文件瞬间不可读），子进程就返回非零但**没有**带名字的
FAILED 行，于是 `failures` 为空或不含名字，那条断言必红；
而同一条用例里 `ok is False` 的断言反而照样通过。
——这正好复现了门禁报告里"1 failed，且失败的是这一条"的现场。

────────────────────────────────────────────

   -> 说明"正常路径会漂移"这个流行解释不成立，红一定来自**非正常收场**。

2) 我强制把内层 pytest 的超时压到 0.3 秒（模拟极端拥堵），复现：
      _run(...) 返回 {'ok': False, 'returncode': -1,
                      'summary': '阶段超时（超过 0.3 秒），已放弃该阶段',
                      'failures': []}
   于是：
      assert ok is False                -> True   （通过）
      assert any("test_alpha" in ...)   -> False  （**红**）
      assert any("ERROR" in ...)        -> False  （**红**）
   -> **触发路径 A（超时）已证实。**

3) 我模拟"临时文件在写入与运行之间消失"（AV 锁 / 临时目录被清 / 运行期

   -> **触发路径 B（文件瞬时不可读/收集期报错）已证实。**

────────────────────────────────────────────
二、为什么只在"全量门禁"里红、单独跑永远绿
────────────────────────────────────────────
两条触发路径都需要**外部环境异常**，而单独跑该文件时环境是干净的：
  - A 需要极端拥堵（本项目开发记录里已实测过并发把耗时拖到 900 倍量级）；
  - B 需要 AV / 临时目录 / 仓库写入者恰好在这一瞬动手。
而全量门禁跑 15~16 分钟、且**总有别的方在同一个仓库里写文件**
（17:55 那次红，报告里 `source_changed_during_run=True`，就是运行期有人
动了 scripts\verify_project.py）。环境异常只在这段窗口里才可能出现。

────────────────────────────────────────────
二·补、按耗时推算：17:55 那次更可能是 B，不是 A
────────────────────────────────────────────
我把三次全量门禁的 pytest 阶段耗时摆到一起，按"秒/用例"比：
  17:55（红） 1 failed, 669 passed in 571.83s  -> 670/571.83 = 0.853 秒/用例
  18:52（绿） 674 passed in 902.53s            -> 674/902.53 = 1.339 秒/用例
  19:13（绿） 674 passed in 959.71s            -> 674/959.71 = 1.424 秒/用例
也就是说，17:55 那次比两次正常跑**还快约 1.6 倍**，机器当时并不拥堵。
若内层 pytest 真被拖到 300 秒（≈150 倍），整轮不可能只花 571 秒 ——
**所以触发路径 A（超时）在 17:55 基本可以排除**；那一次更可能是 B
（临时文件瞬时不可读 / 收集期报错）。这与报告里
`source_changed_during_run=True`（运行期确有别的方在写仓库）互相印证。
—— 这条把"是 A 还是 B"从"完全未知"收窄到"更可能是 B"。

更硬的一版算法（用总时长反推）：内层 pytest 的超时是 300 秒。如果 A 成立，
光是这条用例就要占掉 ≥300 秒；而 17:55 那一整轮（670 个用例）只跑了 571.83 秒。
扣掉这 300 秒，剩下 669 个用例只有约 271 秒 —— 对照两次绿跑里
669 个用例约需 900 秒，等于那台机器当时比正常**快 3 倍以上**。
这在物理上讲不通。所以 **A 不成立，17:55 是 B 类（非超时的异常收场）**。

另：我查了本机 Defender 状态，`Get-MpComputerStatus` / `Get-MpPreference`
都报"提供程序加载失败"（本机疑似已移除/关闭 Defender）。所以 B 的
"杀软锁文件"这一支**证据不足**；B 更可能来自**并发写入者 / 并发 pytest 会话
对共享临时目录的干扰**（我实测到 TEMP 下同时存在多个 pytest-NNNN 基线目录）。

五、我建议的最小修法（本轮未改代码，原因见六）
────────────────────────────────────────────
根因是**用例把"门禁没抓到名字"和"子进程没跑成"混成同一件事**。
最小且不削弱契约的改法：给这条用例加一个前置守卫 ——
当 `result["returncode"] == -1`（超时）或失败行是"收集期报错/文件不存在"
这类**子进程没跑成**的形态时，判为环境性不可判、**重试**（有限次），
只有子进程确实干净跑完、却仍没抓到名字时才算门禁缺陷。
更彻底但不必要的做法是把 `_run` 的解析逻辑抽成纯函数单独测，
把这条端到端用例降级成冒烟测试。

七、我落地的修法（最小改动，只在用例里）
────────────────────────────────────────────
根因是**用例把"门禁没抓到名字"和"子进程根本没跑成"混成同一件事**，
所以我在 `tests\test_verify_project_gate.py` 这条用例里加了一个本地小函数
`_run_until(command, timeout, want)`：跑子命令，**只在没拿到想要的结果时**
重试有限次（共 3 次），然后照旧断言。
为什么这样既修好又不削弱契约：
  - 环境性异常（超时 / 文件瞬时不可读）**下一次通常就好了** -> 重试能恢复；
  - 门禁的 failures 解析若**真的坏了**，它是确定性的，重试 3 次仍然抓不到名字
    -> 照样红，不会把真缺陷放过去。
我没有改 `_run` 本身：它在超时时返回 `failures=[]` 是**正确**的
（子进程都没跑完，本来就没有"失败用例名"可给）。

我执行的验证（注入式，不是"跑一遍看看"）：
1) 用代理 gate 把**第 2 次子进程调用**强制变成异常收场：
   - 形状 B（rc=4、failures=['ERROR: file or directory not found: X']）-> 用例 **PASS**；
   - 形状 A（rc=-1、failures=[]、summary='阶段超时...'）-> 用例 **PASS**；
2) 对照：把**每一次**调用都变成异常收场（模拟"解析真的坏了"）-> 用例 **如期红**；
3) tests\test_verify_project_gate.py：16 passed；
4) 连带跑会检查测试文件的用例（bytecode policy / docstring integrity / run_tests guard）
   共 22 passed；
5) 全量门禁（00:14:25）：**PASS，692 passed in 577.12s**，含我的改动。
