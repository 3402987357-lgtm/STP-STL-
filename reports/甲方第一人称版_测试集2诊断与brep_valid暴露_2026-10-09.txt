一、我这一轮要做什么

上一轮结束时补成封闭实体是 6/9，剩下 3 个未成：

- `测试集/2`：缝已合到 0.0228 mm 但 solids=0、valid=False
- `测试集/1`：缝总长 0.1325 mm 仍超容差
- `训练集/4`：本来就封闭，已改为不动它

这一轮我去查 `测试集/2` 的 Shell 到底卡在哪。

二、我查到的事实

事实 1：它的开口只有 8 条微小缝，不是大洞

  8 条自由边长度分别是 0.003157 / 0.003719 / 0.005305 / 0.006074 /
  0.009218 / 0.009418 / 0.009525 / 0.012062 mm，**合计约 0.0228 mm**，
  远低于 0.05 mm 几何容差。所以它确实是"缝已合上"。

事实 2：不是面朝向问题

  141 个面里 140 个正向、1 个反向。我试了
  `ShapeFix_Shell.FixFaceOrientation` 的三种参数组合（default /
  nonmanifold / no-multiconex），**全部返回 False 且朝向没变**
  （仍是 140/1）。所以朝向不是卡点，或者 OCP 修不动它。

事实 3：ShapeAnalysis 认为它没问题

  `ShapeAnalysis_Shell.HasFreeEdges() = False`、
  `HasBadEdges() = False`，但 `BRepCheck_Analyzer.IsValid() = False`。
  两套检查结论不一致。

事实 4（重要，更正我上一轮的说法）：**它的写出文件是有效的**

  我加了 `brep_valid` 字段（写出文件重读后做 BRepCheck），实测：

      测试集/2 | solid=0 | gap 1.6138->0.0228 | closed=False | brep_valid=True

  也就是说：**我上一轮说"测试集/2 在所有 6 档容差下都建不出有效
  Solid"是对的，但我同时说它 valid=False 是误导的**——那是内存中间
  形状的状态，甲方真正拿到的 STEP 文件是有效的。

  这与我更早发现的"内存与写出文件拓扑不一致"是同一类问题的又一例。

三、我没能做到的事

**我没有查明 `测试集/2` 为什么建不出有效 Solid。**

我想从 BRepCheck 拿具体失败原因，但 OCP 的 Python 绑定没有暴露
BRepCheck 的状态枚举：`analyzer.Result(shape).Minimum()` 返回 `None`、
逐面检查 141 个面全部返回 `None`。诊断这条路走不通。

我不再在诊断工具上耗，改为把这个状态如实暴露给甲方。

四、我做的改进：如实暴露 brep_valid

真实件基准的每个记录新增 `brep_valid` 字段：**写出文件重读后**做
BRepCheck 的结果。理由：内存里的中间形状状态对甲方没有意义，甲方
拿到的是文件，所以有效性必须以文件为准。

实测 9 个件：

| 件 | Solid | 缝总长 前→后 | closed | brep_valid |
|---|---|---|---|---|
| 测试集/4 | 1 | 4.1484→0.0246 | True | True |
| 测试集/5 | 1 | 4.4133→0.0104 | True | True |
| 测试集/6 | 1 | 1.3756→无 | True | True |
| 测试集/7 | 1 | 2.1217→0.0014 | True | True |
| 训练集/7 | 1 | 12.5544→0.0204 | True | True |
| 训练集/8 | 1 | 9.2468→0.0115 | True | True |
| 测试集/2 | 0 | 1.6138→0.0228 | False | **True** |
| 测试集/1 | 1 | 3.5010→0.1325 | False | **False** |
| 训练集/4 | - | 0.0112→未动 | False | None（未写出） |

**关键新增信息：`测试集/1` 的写出文件 brep_valid=False**——它比我
先前报告的更糟：不只是缝超容差，文件本身的有效性检查也没过。这个
信息原先是缺失的。
