我方二进制 STL 头部换行误判修复记录
日期：2026-10-07
项目根目录：D:\STP_STL_Missing_Region_Recognition

一、我为什么要做这件事

我方在复核 STL 类型判定时，构造了一组极端输入，发现一个真实的假拒绝：
合法的二进制 STL，如果它的 80 字节头部里含有换行，就会被 load_stl 拒绝，
而且报的是一句与事实不符的错误：

  我发现 ASCII STL 不包含任何三角面：...\with_newline.stl

我用最小复现确认了这一点。二进制 STL 的头部是 80 字节自由文本，很多导出器会
写成 "solid 零件名"，其中一部分会带上换行或 CRLF。也就是说，这是一个完全
可能出现在甲方真实数据里的输入，却会被我方当成坏文件挡掉。

二、根因

问题出在 geometry\stl.py 的 _has_plausible_binary_layout：

1. 它先判断 data[:80] 里有没有 \n 或 \r，命中就直接 return False；
2. 这一步跑在了 _has_exact_binary_size 之前，于是"头部带换行的二进制 STL"
   根本没机会走到长度精确匹配这个最强的二进制信号；
3. 接着 _looks_like_ascii_stl 会因为二进制体里没有 facet/vertex 也返回 False；
4. 最后落到 _looks_like_ascii_stl_header（只要以 solid 开头就返回 True），
   抛出"ASCII STL 不包含任何三角面"这个与事实相反的错误。

三、我方怎么改

我把长度精确匹配提到换行启发式之前：

  if len(data) < 84: return False
  if _has_exact_binary_size(data): return True      # 新增：最强信号优先
  if b"\n" in data[:80] or b"\r" in data[:80]: return False
  ...

为什么这样是安全的：二进制 STL 的精确长度满足 84 + 50n == len(data)，其中 n 是
偏移 80 处的 4 字节小端整数。ASCII 文本要在偏移 80 处凑出这个 n，需要第 2、3、4
个字节全为 NUL，而 ASCII STL 里不会有 NUL，所以不会把文本文件误判成二进制。
